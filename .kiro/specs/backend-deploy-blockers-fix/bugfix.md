# Bugfix Requirements Document

## Introduction

El backend serverless (Lambda + API Gateway + DynamoDB + SQS + EventBridge Scheduler, gestionado con Terraform) tiene 4 bloqueadores reales que impiden un despliegue funcional de extremo a extremo. Los 4 fueron verificados directamente contra el código Python en `backend/` y contra `terraform/modules/lambda/main.tf` / `terraform/modules/iam/main.tf` — no contra documentación ni contra `tasks.md` de specs previas:

1. El handler de la Lambda `api` (y `orquestador`, que reutiliza el mismo código `backend/main.py`) está configurado en Terraform como `"main.handler"`, pero el código real vive en `backend/main.py` con imports internos (`from backend.shared...`, `from backend.api.routes...`) que solo resuelven si el `.zip` preserva la estructura de paquete `backend/`. Existe un comentario `FLAGGED` en el propio `terraform/modules/lambda/main.tf` (líneas ~48-53) que admite esta ambigüedad sin resolverla, y un archivo huérfano `lambda_handler.py` en la raíz que documenta una alternativa (`"lambda_handler.handler"`) nunca aplicada en Terraform.
2. Los handlers de `scan-worker` y `scoring-worker` en Terraform también son `"main.handler"`, pero el código expone `handler_scan_worker()` y `handler_scoring_worker()` respectivamente — un desajuste directo de nombre de función que no resuelve bajo ninguna estructura de `.zip`.
3. No existe ningún script de empaquetado ejecutable: los 3 workflows de GitHub Actions (`backend-deploy.yml`, `frontend-deploy.yml`, `terraform-apply.yml`) están vacíos (0 líneas), no hay `Makefile`/`build.sh`/`setup.py`, y el único script en `scripts/` (`export-openapi.py`) es para el OpenAPI del frontend, sin relación con Lambdas. **Decisión de alcance explícita:** esta spec no solo crea el script de empaquetado, también conecta `.github/workflows/backend-deploy.yml` a él (ver criterio 2.7) — `frontend-deploy.yml` y `terraform-apply.yml` permanecen vacíos, sin tocar, fuera de alcance.
4. La Lambda `api` se auto-invoca de forma asíncrona (`backend/api/routes/profile.py`, `_trigger_async_resumen_generation`, líneas ~137-141, vía `boto3.client("lambda").invoke(...)`) para generar `resumenParaMatching`, pero su rol IAM (`aws_iam_role_policy.api_policy` en `terraform/modules/iam/main.tf`) no incluye `lambda:InvokeFunction`.

**Fuera de alcance de esta spec (explícito, no se toca aquí):**

- **`notificador`**: su handler (`backend.workers.notificador.handler.handler`) ya está correctamente configurado en Terraform y verificado — no se modifica.
- **Lógica de negocio de cualquier worker** (cascada de descubrimiento, missCount, prefiltro de cargos, prompt de scoring, etc.) — esta spec solo toca cómo se expone/empaqueta/despliega el código, nunca qué hace.
- **Tarea 8 pendiente de `backend-scan-y-scoring`** (inmutabilidad de `firstSeenAt`) — tema aparte, no se reabre.
- **Los `event_source_mapping` de SQS** (scan-worker, scoring-worker) **y de DynamoDB Streams** (notificador) — ya están definidos en Terraform y verificados; no se crean ni modifican, solo dependen de que estos 4 bloqueadores se resuelvan para que el `apply` real tenga efecto.
- **Cambios de IAM en roles distintos a `api_role`** — orquestador, scan-worker, scoring-worker, notificador, EventBridge Scheduler y GitHub Actions ya tienen los permisos que necesitan para lo que hacen hoy; esta spec no les agrega ni quita nada.
- **`frontend-deploy.yml` y `terraform-apply.yml`** — permanecen vacíos (0 líneas), sin modificar. El alcance de CI/CD de esta spec se limita a conectar `backend-deploy.yml` al script de empaquetado de las 5 Lambdas (criterio 2.7).

**Metodología de verificación aplicable a todos los criterios de aceptación de esta spec:** ningún criterio se puede marcar como resuelto solo por "verse correcto en el código". Cada criterio de aceptación (Sección 2) exige evidencia concreta — comando ejecutado (`terraform validate`, `terraform plan`, invocación local de un import de Python, inspección del `.zip` generado) o cita de archivo+línea. Lo que requiere AWS real (permisos IAM efectivos en ejecución, que el `.zip` subido funcione al invocarse de verdad) queda marcado explícitamente como pendiente de verificación post-implementación en el criterio correspondiente, nunca asumido como resuelto en esta sesión.

**Nota — nombres reales de bucket confirmados desde la consola de AWS:** el bucket real de código Lambda es `job-search-lambda-code-5155151158151`. El valor actual en `terraform/terraform.tfvars` (`lambda_code_bucket = "job-search-lambda-code"`) está desactualizado — le falta el sufijo de cuenta `-5155151158151` — y SHALL corregirse como parte de la implementación del criterio 2.8, no solo el patrón de la policy IAM; de lo contrario ningún despliegue real funcionaría independientemente de que el patrón IAM esté corregido. El bucket de Terraform state, `job-search-terraform-state-5543569870`, ya está correcto en `terraform.tfvars` (`terraform_state_bucket = "job-search-terraform-state-5543569870"`) y no requiere corrección de valor — solo el patrón de la policy IAM que lo referencia (ver 2.8.1) está roto.

## Bug Analysis

### Current Behavior (Defect)

**Bloqueador 1 — Handler ambiguo de `api`/`orquestador` (C(X): Lambda usa `backend/main.py` con imports `from backend...` Y Terraform configura `handler = "main.handler"`):**

1.1 WHEN se empaqueta y despliega la Lambda `api` con `handler = "main.handler"` (`terraform/modules/lambda/main.tf`, resource `aws_lambda_function.api`, comentario FLAGGED ~líneas 48-53) mientras el código real vive en `backend/main.py` usando imports internos que requieren la estructura de paquete `backend/` completa, THEN el sistema falla en tiempo de invocación con `Runtime.HandlerNotFound` o `ImportModuleError`, porque no existe un módulo `main` en la raíz del `.zip` que satisfaga esos imports bajo ese nombre de handler.

1.2 WHEN se empaqueta y despliega la Lambda `orquestador` con `handler = "main.handler"` (`terraform/modules/lambda/main.tf`, resource `aws_lambda_function.orquestador`), reutilizando el mismo `backend/main.py` que `api`, THEN el sistema falla de forma idéntica a 1.1, por la misma causa raíz.

**Bloqueador 2 — Mismatch directo de nombre de función en `scan-worker`/`scoring-worker` (C(X): la función expuesta en el módulo no se llama `handler`):**

1.3 WHEN se empaqueta y despliega la Lambda `scan-worker` con `handler = "main.handler"` (`terraform/modules/lambda/main.tf`, resource `aws_lambda_function.scan_worker`), THEN el sistema falla porque `backend/workers/scan_worker.py` expone únicamente `handler_scan_worker()`, no un atributo llamado `handler` — esto no resuelve bajo ninguna estructura de `.zip`, independientemente de cómo se empaquete.

1.4 WHEN se empaqueta y despliega la Lambda `scoring-worker` con `handler = "main.handler"` (`terraform/modules/lambda/main.tf`, resource `aws_lambda_function.scoring_worker`), THEN el sistema falla porque `backend/workers/scoring_worker.py` expone únicamente `handler_scoring_worker()`, no un atributo llamado `handler` — misma causa raíz que 1.3.

**Bloqueador 3 — Ausencia de script de empaquetado (C(X): se necesita un `.zip` en S3 para que exista el recurso Lambda funcional Y no existe ningún proceso repetible que lo produzca):**

1.5 WHEN un desarrollador o pipeline de CI intenta preparar un despliegue real (`terraform apply` seguido de una invocación de cualquiera de las 5 Lambdas), THEN el sistema no provee ningún script ejecutable de empaquetado: los 3 workflows de GitHub Actions (`.github/workflows/backend-deploy.yml`, `frontend-deploy.yml`, `terraform-apply.yml`) están vacíos (0 líneas, verificado), no existe `Makefile`/`build.sh`/`setup.py` en la raíz del repo, y el único script en `scripts/` (`export-openapi.py`) genera el `openapi.json` del frontend sin relación con el empaquetado de Lambdas — por lo que los `.zip` esperados en `s3://{lambda_code_bucket}/{lambda_code_key_prefix}/{nombre_funcion}/code.zip` (ruta leída por `terraform/modules/lambda/main.tf` vía `s3_key` en cada `aws_lambda_function.*`, con `lambda_code_key_prefix` definido en `terraform/variables.tf`) nunca se generan ni suben mediante ningún proceso repetible.

**Bloqueador 4 — Permiso IAM faltante para auto-invocación de `api` (C(X): el código invoca `lambda:InvokeFunction` sobre sí mismo Y la policy del rol no lo incluye):**

1.6 WHEN el handler `_trigger_async_resumen_generation` en `backend/api/routes/profile.py` (líneas ~137-141, invocado desde `PUT /me/profile` y `POST /me/profile/roles/suggest`) ejecuta `boto3.client("lambda").invoke(FunctionName=os.environ["AWS_LAMBDA_FUNCTION_NAME"], InvocationType="Event", ...)`, THEN la llamada falla con `AccessDeniedException`, porque `aws_iam_role_policy.api_policy` en `terraform/modules/iam/main.tf` no otorga la acción `lambda:InvokeFunction` sobre ningún recurso.

### Expected Behavior (Correct)

2.1 WHEN se empaqueta y despliega la Lambda `api`, THEN el sistema SHALL configurar un atributo `handler` en Terraform y una estructura de `.zip` mutuamente consistentes entre sí (Opción A: `handler = "backend.main.handler"` con el `.zip` preservando el paquete `backend/`; u Opción B: `handler = "lambda_handler.handler"` empaquetando `lambda_handler.py` junto a `backend/` — decisión técnica a fijar en `design.md`), de forma que AWS Lambda localice y ejecute el entry point sin `HandlerNotFound`/`ImportModuleError` — verificable localmente ejecutando `python -c "import <módulo_resuelto>"` (o el equivalente `from <módulo> import handler`) desde una réplica de la estructura del `.zip`, y mediante `terraform validate`/`terraform plan` sin errores sobre el atributo `handler`.

2.2 WHEN se empaqueta y despliega la Lambda `orquestador` (que reutiliza `backend/main.py`), THEN el sistema SHALL aplicar la misma resolución consistente handler/empaquetado que 2.1, verificable de la misma forma.

2.3 WHEN se empaqueta y despliega la Lambda `scan-worker`, THEN el sistema SHALL exponer un entry point literalmente llamado `handler` (por renombrado de `handler_scan_worker` a `handler`, o por un wrapper dedicado) en la ruta de módulo que configure el atributo `handler` de Terraform para `scan_worker` — verificable con `python -c "from <módulo_resuelto> import handler"` ejecutándose sin error.

2.3.1 WHEN se renombra `handler_scan_worker` a `handler` (o se agrega un wrapper) en `backend/workers/scan_worker.py`, THEN el sistema SHALL actualizar también `backend/tests/test_scan_worker.py`, que hoy importa `handler_scan_worker` por nombre literal en las líneas 140, 179, 273, 302 y 331 (`from backend.workers.scan_worker import handler_scan_worker`), y lo invoca en las líneas 160, 209, 286, 315 y 343 (además de 396, que ya usa una variable local `event` distinta) — de forma que la suite completa de tests SHALL seguir pasando con el mismo conteo de `passed` que tenía antes del cambio de nombre, verificable ejecutando `pytest` antes y después del renombrado y comparando el resultado. Si existen fallos preexistentes no relacionados con este fix (por ejemplo en `backend/tests/test_logging_config.py` u otro módulo), estos SHALL documentarse explícitamente en `design.md` como preexistentes antes de excluirlos de la comparación — no se asume su existencia sin verificarlo primero contra la suite real.

2.4 WHEN se empaqueta y despliega la Lambda `scoring-worker`, THEN el sistema SHALL exponer un entry point literalmente llamado `handler` en la ruta de módulo que configure el atributo `handler` de Terraform para `scoring_worker` — verificable de la misma forma que 2.3.

2.4.1 WHEN se renombra `handler_scoring_worker` a `handler` (o se agrega un wrapper) en `backend/workers/scoring_worker.py`, THEN el sistema SHALL actualizar también `backend/tests/test_scoring_worker.py`, que hoy importa `handler_scoring_worker` por nombre literal en las líneas 225, 263, 315, 375 y 418 (`from backend.workers.scoring_worker import handler_scoring_worker`), y lo invoca en las líneas 242, 292, 349, 393 y 446 — de forma que la suite completa de tests SHALL seguir pasando con el mismo conteo de `passed` que tenía antes del cambio de nombre, bajo la misma metodología de comparación pytest antes/después descrita en 2.3.1.

2.5 WHEN un desarrollador o pipeline de CI necesita desplegar el backend, THEN el sistema SHALL proveer un script de empaquetado ejecutable (ubicación y forma exacta a definir en `design.md`) que: (a) construya un `.zip` por cada una de las 5 Lambdas (`api`, `orquestador`, `scan_worker`, `scoring_worker`, `notificador`) con la estructura de paquete decidida en 2.1-2.4 (y la estructura ya vigente y no tocada para `notificador`), (b) instale las dependencias declaradas en `backend/pyproject.toml`, y (c) SHALL subir efectivamente cada `.zip` generado a la ruta exacta `s3://{lambda_code_bucket}/{lambda_code_key_prefix}/{nombre_funcion}/code.zip` que espera `terraform/modules/lambda/main.tf` (no basta con dejarlo en un path local) — sin riesgo de drift de estado de Terraform, dado que `terraform/modules/lambda/main.tf` (líneas ~26-29, sección "Lambda Code Deployment Strategy") documenta explícitamente que Terraform nunca gestiona el objeto S3 como recurso propio (no existe ningún `aws_s3_object`/`aws_s3_bucket_object` en el módulo, verificado leyendo el archivo completo) y que todos los `aws_lambda_function.*` referencian el código únicamente vía `s3_bucket`/`s3_key` (nunca `filename`), esperando que el objeto ya exista en S3 antes del `apply`. Verificable ejecutando el script localmente (contra un bucket de prueba o en modo `--dry-run`) e inspeccionando el contenido del `.zip` producido, confirmando la subida real vía `aws s3api head-object` (o equivalente), y comparando las claves S3 calculadas contra las citadas literalmente en el `.tf`.

2.6 WHEN la Lambda `api` ejecuta la auto-invocación de `_trigger_async_resumen_generation`, THEN el sistema SHALL otorgar al rol IAM de `api` un permiso `lambda:InvokeFunction` restringido al ARN de la propia función (nunca `"*"`), construido como string literal (`"arn:aws:lambda:*:*:function/job-search-api"`, o el equivalente con variables de región/account_id si el proyecto ya las expone como data source) — **restricción de diseño explícita**: el ARN NUNCA SHALL referenciar `aws_lambda_function.api.arn` directamente, dado que crearía un ciclo `aws_iam_role_policy.api_policy` → `aws_lambda_function.api` (vía `role = var.api_role_arn`, que depende de la policy) → `aws_iam_role.api_role` → de vuelta a la policy. Este patrón de construir el ARN por nombre conocido en vez de por referencia directa ya tiene precedente exacto en el propio código: `terraform/modules/iam/main.tf`, resource `aws_iam_role_policy.eventbridge_scheduler_policy`, resuelve el mismo problema construyendo `"arn:aws:lambda:*:*:function/job-search-orquestador"` como literal en vez de referenciar `aws_lambda_function.orquestador.arn` — verificable mediante `terraform plan`/`terraform validate` mostrando el nuevo statement de policy con `Resource` igual al ARN literal de `job-search-api`, y confirmando que no se introduce un ciclo de dependencia entre módulos `iam` y `lambda`. **Pendiente de verificación post-implementación** (no verificable en esta sesión sin AWS real): que la invocación efectivamente deje de fallar con `AccessDeniedException` al ejecutarse en la cuenta real.

2.7 WHEN se completan los criterios 2.1-2.6 de esta spec, THEN el sistema SHALL implementar `.github/workflows/backend-deploy.yml` (dejando de estar vacío) invocando el script de empaquetado definido en 2.5 para las 5 Lambdas, autenticándose vía OIDC contra el rol `aws_iam_role.github_actions` ya existente en `terraform/modules/iam/main.tf` (sin claves de larga vida, consistente con el stack cerrado del proyecto), y disparándose en push a `main` o manualmente vía `workflow_dispatch` — la decisión exacta de trigger(s) a fijar en `design.md`. Verificable inspeccionando el YAML resultante contra el rol OIDC citado y, si es posible, mediante una ejecución de prueba del workflow (`workflow_dispatch` manual) sin necesidad de un push real a `main`.

**Nota — prerequisito de 2.7:** los criterios 2.8 y 2.8.1 (corrección del patrón de recurso S3 en `github_actions_policy`, tanto para el bucket de código Lambda como para el bucket de Terraform state) son prerequisito para que 2.7 funcione en la práctica. Sin 2.8/2.8.1, el workflow implementado en 2.7 fallaría con `AccessDeniedException` al intentar subir el `.zip` de cada Lambda al bucket real (`job-search-lambda-code-5155151158151`), porque el patrón de recurso S3 vigente en la policy nunca matchea ese nombre de bucket.

2.8 WHEN el workflow `.github/workflows/backend-deploy.yml` (implementado en 2.7) intenta subir el `.zip` de una Lambda al bucket real `job-search-lambda-code-5155151158151` usando el rol `aws_iam_role.github_actions`, THEN el sistema SHALL corregir el statement S3 de `aws_iam_role_policy.github_actions_policy` en `terraform/modules/iam/main.tf` de forma que el patrón de recurso coincida con el nombre real del bucket (`job-search-lambda-code-5155151158151`, obtenido de la variable `lambda_code_bucket` ya existente en `terraform.tfvars`, nunca hardcodeado como string literal), reemplazando el patrón actual `"arn:aws:s3:::*-lambda-code-bucket"` / `"arn:aws:s3:::*-lambda-code-bucket/*"` (que exige que el nombre del bucket termine literalmente en `-lambda-code-bucket`, y por lo tanto nunca matchea `job-search-lambda-code-5155151158151`, que termina en el sufijo de cuenta `-5155151158151`) por un patrón que sí matchee. Como parte de este criterio, el sistema SHALL también corregir el valor desactualizado de `lambda_code_bucket` en `terraform/terraform.tfvars` (actualmente `"job-search-lambda-code"`, sin el sufijo `-5155151158151`) para que refleje el nombre real del bucket — sin esta corrección de valor, ningún despliegue real funcionaría independientemente de que el patrón IAM esté corregido. **Esta es una corrección de un recurso (`Resource`) mal escrito en una policy ya existente, NO la adición de un permiso nuevo**: las acciones `s3:PutObject`, `s3:GetObject`, `s3:ListBucket` y `lambda:UpdateFunctionCode` ya están otorgadas en `github_actions_policy` (verificado leyendo el archivo completo — el statement Lambda de la misma policy ya otorga `lambda:UpdateFunctionCode` con `Resource = "*"`, sin cambios necesarios ahí); solo el ARN de recurso del statement S3 estaba mal escrito. Verificable mediante `terraform plan` mostrando el cambio de `Resource` en ese statement específico, sin ningún otro cambio de `Action` en la policy. **Excepción explícita y documentada a la cláusula 3.4** (ver 3.4 ajustada).

2.8.1 WHEN el mismo workflow `.github/workflows/backend-deploy.yml` (implementado en 2.7), a través de `terraform-apply.yml` o de cualquier operación de Terraform que use el rol `aws_iam_role.github_actions`, necesita leer/escribir el estado de Terraform en el bucket real `job-search-terraform-state-5543569870`, THEN el sistema SHALL corregir también, en el mismo statement S3 de `aws_iam_role_policy.github_actions_policy`, el patrón de `Resource` para el bucket de Terraform state, reemplazando `"arn:aws:s3:::*-terraform-state-bucket"` / `"arn:aws:s3:::*-terraform-state-bucket/*"` (que exige que el nombre del bucket termine literalmente en `-terraform-state-bucket`, y por lo tanto nunca matchea `job-search-terraform-state-5543569870`, que termina en el sufijo de cuenta `-5543569870`) por un patrón que referencie `var.terraform_state_bucket` (variable ya declarada en `terraform/variables.tf`), de forma que coincida con el nombre real `job-search-terraform-state-5543569870` — exactamente el mismo tipo de desajuste ya identificado y corregido para el bucket de código en 2.8, aplicado aquí al bucket de state. **Prerequisito explícito de este criterio**: hoy el módulo `iam` no recibe ninguna variable de entrada — `terraform/main.tf`, bloque `module "iam"`, dice explícitamente "No input variables - IAM module creates all roles with hardcoded names", y `terraform/modules/iam/` no tiene ningún archivo `variables.tf` (solo `main.tf` y `outputs.tf`, verificado con listado de directorio). Por lo tanto, para que `github_actions_policy` referencie `var.lambda_code_bucket`/`var.terraform_state_bucket` (en vez de un string hardcodeado o de un patrón wildcard roto), el sistema SHALL: (a) crear `terraform/modules/iam/variables.tf` declarando ambas variables (`lambda_code_bucket` y `terraform_state_bucket`), y (b) actualizar el bloque `module "iam"` en `terraform/main.tf` para pasarlas explícitamente (`lambda_code_bucket = var.lambda_code_bucket`, `terraform_state_bucket = var.terraform_state_bucket`) — ambas variables ya existen a nivel raíz en `terraform/variables.tf`, no es necesario crearlas ahí. Verificable mediante `terraform plan` mostrando el cambio de `Resource` en ambos sub-patrones (lambda-code y terraform-state) del mismo statement, sin ningún otro cambio de `Action`. **Excepción explícita y documentada a la cláusula 3.4** (ver 3.4 ajustada).

### Unchanged Behavior (Regression Prevention)

3.1 WHEN se empaqueta y despliega la Lambda `notificador`, THEN el sistema SHALL CONTINUE TO usar `handler = "backend.workers.notificador.handler.handler"` exactamente como ya está configurado en `terraform/modules/lambda/main.tf`, sin modificaciones por esta spec.

3.2 WHEN se ejecuta la lógica de negocio de cualquier worker (cascada de descubrimiento, clasificación de escaneo, aplicación de `missCount`, prefiltro de cargos, prompt y validación de scoring, generación de `resumenParaMatching`, etc.), THEN el sistema SHALL CONTINUE TO comportarse exactamente igual que antes de este fix — esta spec solo cambia cómo se expone el entry point y cómo se empaqueta/despliega el código, nunca qué hace ese código.

3.3 WHEN se evalúan los `event_source_mapping` de SQS para `scan-worker`/`scoring-worker` (`aws_lambda_event_source_mapping.scan_worker_sqs`, `scoring_worker_sqs`) y el de DynamoDB Streams para `notificador` (`notificador_dynamodb_stream`), THEN el sistema SHALL CONTINUE TO usar exactamente las definiciones ya presentes en `terraform/modules/lambda/main.tf`, sin recrearlas ni modificarlas.

3.4 WHEN se evalúa cualquier rol IAM distinto de `api_role` (`orquestador_role`, `scan_worker_role`, `scoring_worker_role`, `notificador_role`, `eventbridge_scheduler_role`, `github_actions`), THEN el sistema SHALL CONTINUE TO tener exactamente los mismos permisos que tenía antes de este fix — ningún nuevo grant, ninguna revocación — **EXCEPCIÓN EXPLÍCITA Y DOCUMENTADA**: el statement S3 de `aws_iam_role_policy.github_actions_policy` (rol `github_actions`) SÍ cambia, conforme a los criterios 2.8 y 2.8.1, limitándose estrictamente a corregir el patrón del ARN de `Resource` para AMBOS sub-patrones del mismo statement — el del bucket de código Lambda (para que coincida con el bucket real `job-search-lambda-code-5155151158151`, criterio 2.8) y el del bucket de Terraform state (para que coincida con el bucket real `job-search-terraform-state-5543569870`, criterio 2.8.1) — las acciones (`Action`) de ese statement no cambian, ningún permiso nuevo se otorga y ninguna acción se agrega o quita; es la corrección de dos ARNs mal escritos que nunca coincidieron con los buckets reales, no una ampliación de alcance.

3.5 WHEN se considera la Tarea 8 pendiente de `backend-scan-y-scoring` (inmutabilidad de `firstSeenAt`), THEN el sistema SHALL CONTINUE TO dejar esa tarea sin tocar — fuera de alcance de esta spec.

3.6 WHEN los contratos ya establecidos en `.kiro/specs/backend-core/design.md` y `.kiro/specs/backend-scan-y-scoring/design.md` (timeouts de Lambda, concurrencia reservada, nombres de variables de entorno, esquemas de mensajes SQS) se comparan contra los cambios de empaquetado hechos en esta spec, THEN el sistema SHALL CONTINUE TO satisfacerlos sin romperlos — verificable mediante una verificación cruzada explícita, citando archivo+línea de ambos documentos de diseño reales (no resúmenes), a realizar como parte de `design.md` de esta spec antes de cerrarla como resuelta.
